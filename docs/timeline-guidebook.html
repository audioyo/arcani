How to update this guidebook

Rule: update this file every time a section is completed and a commit and/or push is made.

A "section" is any checklist item below: a workflow step (spec, failing tests, implementation, review, CI, merge) or an acceptance criterion. This guidebook is the human-readable view of the timeline. sprint-status.yaml stays the machine record; keep them in step.

  1. Open docs/timeline-guidebook.html in your editor and scroll to the block marked DATA: EDIT HERE near the bottom.
  2. Find the story by its id (for example id: "0.4").
  3. Tick each finished workflow step: change false to true in its steps list. Add the commit hash in the step's note if you like.
  4. Tick each finished acceptance criterion: change [" ", "..."] to ["x", "..."] (use "~" for partly done).
  5. Set the story's status to match sprint-status.yaml: backlog, ready-for-dev, in-progress, review, or done.
  6. Add one line at the top of UPDATE_LOG: date, short commit hash, and what was finished. Write "pushed" or "PR #N merged" when that happened.
  7. Change LAST_UPDATED and, if the focus moved, CURRENT and NEXT.
  8. Save, reload the page in the browser to check it, then commit it with the work or as a small follow-up commit: Update timeline guidebook (Story X.Y ...).

Instruction for agents (copy this into any story prompt if needed)

"After every commit or push that completes a checklist section, update docs/timeline-guidebook.html: tick the finished steps and acceptance criteria in the DATA block, set the story status to match sprint-status.yaml, add a dated line with the commit hash to the top of UPDATE_LOG, and update LAST_UPDATED, CURRENT, and NEXT. Follow the copy rules: no em dashes, no banned terms, no claim words."

Road map: seven epics to v0.1

Epics run in order. Each dot fills in as its stories finish. v0.1 is done when the gate report passes and all eight starter renders carry Audio's provisional sign-off.

How every story moves (the workflow checklist)

The seven steps per story

  1. Spec: write the story spec in _bmad-output/implementation-artifacts/; Audio approves it.
  2. Failing tests: a fresh-context QA agent commits tests only, and they fail.
  3. Build it: implementation commits; tests pass locally (no commit with failing tests).
  4. Review: code review runs; findings triaged and recorded in the spec.
  5. CI green: fast tier on push; full four-platform tier on the pull request.
  6. Merged: pull request merged into main.
  7. Records: sprint-status.yaml, design log, and this guidebook updated.

Rules for every story

  • Tests first, from the acceptance criteria.
  • Every check has a passing fixture and a must-fail fixture.
  • Every measurement tool is calibrated on Python signals with known answers first.
  • Each story writes only the signal-spec.md section it needs, with worked test vectors, before code uses it.
  • Silence is not evidence: reference matches compare real waveforms.
  • Engine stories join the four-platform hash check at 44.1 and 48 kHz.
  • Thresholds come from the tables. Never hard-code them, never weaken them.
  • One story per branch. Every changed default gets a design log entry.

Glossary

Audio
The sole developer, tester, and listener. Signs off every golden file.
Carrier
The audible tone, in Hz.
Rate
How fast something repeats, in Hz.
AM
Amplitude modulation: a carrier's volume shaped by a slower wave.
Theta reference
A carrier with AM at the theta rate (1 to 6 Hz). It exists in the file, so its phase can be measured.
Gamma PAC layer
A separate carrier with AM at the gamma rate (30 to 60 Hz). Its depth rises and falls with the theta reference and peaks at the coupling phase.
Binaural layer
Two pure sines, one per ear, on their own path. Nothing is coupled to it.
Recipe
One JSON file that fully defines a session.
Signal spec
docs/signal-spec.md, the only source of formulas.
Python reference
An independent renderer the engine must match within -100 dBFS.
Fast tier / full tier
Fast: every push, Windows x64 and Linux. Full: every PR into main and nightly, all four platforms.
AD-9 platforms
Windows x64, Windows arm64, macOS arm64, Android NDK arm64.
Golden file
An approved render stored in Git LFS, bound to a sign-off record with the file's SHA-256.
Determinism key
Recipe hash plus engine version plus sample rate.
Must-fail fixture
A doctored input that proves a check actually catches a fault.
Retrospective
Optional look back at the end of each epic.
